## 2. 数据来源

香港天文台「1901–2100 年公曆與農曆日期對照表」公众年历（繁体中文文本）：

```
https://www.hko.gov.hk/tc/gts/time/calendar/text/files/T{年}c.txt     （年 = 1901..2100）
```

- 200 个文件、73,049 个数据行（1901-01-01 .. 2100-12-31），UTF-8 带 BOM、CRLF。
- 文件结构：标题行 `1901(辛丑-肖牛)年公曆與農曆日期對照表`、列头 `公曆日期 農曆日期 星期 節氣`、逐日数据行。
- 两种排版并存：1901–2010 为 `1901年01月01日`（月日补零），2011–2100 为 `2012年1月1日`（不补零）；解析器兼容两者。
- 另有 37 条「香港於 19xx 年…實施了夏令時間…」说明行（1941–1979），解析时跳过；节气的日期以 HKO 年历表格为准（其夏令时说明不影响农历/节气列）。
- 农历日期列：月首只写月名（`正月`/`閏六月`/`十一月`/`十二月`），其余写日名（`初二`…`三十`；`初一` 只以月首形式出现）；节气列仅在节气日出现（繁体：`驚蟄`/`穀雨`/`小滿`/`芒種`/`處暑`）。

`build-calendar.mjs` 生成时的硬断言（任一失败即 throw、不写文件）：

- 每年数据行 = 365/366、日期连续覆盖全年、星期与公历一致；
- 农历字样连续（月首=月名、其余日号逐日 +1）；
- 每月月长 ∈ {29,30}；每个农历年 12 或 13 个月；闰月至多一个、且紧跟其复制的普通月；闰月序位 ∈ 2..13；
- 每公历年恰好 24 个节气且顺序为 小寒→冬至、偏移严格递增（0..365）；
- 春节（正月初一）严格递增，相邻间隔 353..385 天；
- 1900 年尾部闭合校验（见 §5）；1901-01-01 必须早于 1901 春节。

## 4. 数据格式（10-cal-data.js）

```js
const CAL_DATA = {
  yearBase: 1900,   // years[i] 对应农历年 1900+i（201 条，1900..2100）
  termBase: 1901,   // terms[i] 对应公历年 1901+i（200 条，1901..2100）
  years: [ [startEpoch, monthBits, leapMonth], ... ],
  terms: [ [24 个整数], ... ],
}
```

- `startEpoch`：该农历年正月初一的 epoch day（自 1970-01-01 的整数天数，本地日历语义、与时区无关）。
- `monthBits`：第 k 位(0 起)=1 → 该年第 k+1 个**序位月** 30 天，0 → 29 天。
- `leapMonth`：闰月在**月序中的位置** 1..13（第 leapMonth 个序位是闰月，月号同第 leapMonth-1 个序位），无闰为 0。引擎展开规则：`无闰时 monthNo=pos`；`有闰时 pos<leapMonth→pos`，`pos===leapMonth→闰(leapMonth-1)月`，`pos>leapMonth→pos-1`。
- `terms[i]`：该公历年 24 个节气的 `(epoch - 该年 1 月 1 日 epoch)`，顺序固定为 小寒,大寒,立春,雨水,惊蛰,春分,清明,谷雨,立夏,小满,芒种,夏至,小暑,大暑,立秋,处暑,白露,秋分,寒露,霜降,立冬,小雪,大雪,冬至（与 `Lunar.TERM_KEYS` 一致）。
- 公历换算使用 Howard Hinnant days_from_civil / civil_from_days 纯整数算法（`epochOf`/`dateOf`），不经过 `Date`，无时区/夏令时误差。

## 5. 边界处理

### 5.1 农历 1900 年（`T1900c.txt` 为 404，HKO 年历自 1901 起）

`T1901c.txt` 首行 `1901年01月01日 十一` → 农历 1900 年冬月十一；反推：

- 冬月（11 月）初一 = 1901-01-01 − 10 = **1900-12-22**；
- `1901年01月20日 十二月` → 腊月（12 月）初一 = 1901-01-20，冬月 29 天；
- `1901年02月19日 正月` → 1901 春节 = 1901-02-19，腊月 30 天；1900 农历年共 **384 天 = 13 个月**（该年闰八月）。

因此 `years[0] = [-25537, 0b1010101010101, 9]`：`-25537` = 1900-01-31（1900 正月初一，采用通行万年历值）；1–10 月长度为按「闰八月（闰月序位 9）」的合法占位 `[30,29,30,29,30,29,30,29,30,29,30]`（和 325 天，恰与真实冬月月首 1900-12-22 衔接）；11、12 月为 HKO 推导真实值（29、30 天）。生成时断言 `325 + 29 + 30 = 384`。

> 影响面：**仅 1900 年内日期**（契约数据范围之外）。1901-01-01 起所有换算都只用 1900 年的 11/12 月真实数据，逐日校验已覆盖 1901-01-01..1901-02-18。若要补齐 1900 全年，需要 HKO 未提供的 T1900 数据。

### 5.2 农历 2100 年尾部

`T2100c.txt` 末行 `2100年12月31日 十二月` → 2100-12-31 为腊月初一。2100 农历年 12 个月首（正月 2100-02-09 … 腊月 2100-12-31）全部可见，但**腊月跨入 2101 年，月长无法由 1901–2100 原始数据确定**：

- `monthBits` 末位按 29 天占位（`leapMonth=0`，即 12 个月）；
- `toEpoch(2100, 12, 30)` 返回 `null`；
- `nextSpringFestival(2100-12-31)` 按占位推定为 2101-01-29；
- 若该年实际有「闰十二月」，其月首在 2101 年，数据不可知（对 ≤2100-12-31 的换算无影响）。

### 5.3 其它

- HKO 数据自 1901 小寒（1901-01-05/06）起，`lastTermBefore(1901-01-01..01-04)` 返回 `null`（缺 1900 冬至）；调用方应判空。
- 超范围：`solarTermEpochs(1900|2101)` → `[]`；`solarTermEpoch(越界)` → `null`；`springFestival(1899|2101)` / `toEpoch(越界)` → `null`；`fromEpoch(越界)` 收敛到边界月内最后一天（不抛异常），供 UI 健壮性兜底。

1. **原始数据不入库/不随包**：`tools/hko/raw/` 5.44 MiB 已被 `tools/hko/raw/.gitignore` 忽略；全新环境如需重新生成数据，先 `node tools/hko/fetch.mjs`（需网络）。插件运行时完全离线（数据已内置于 `src/parts/10-cal-data.js`）。
2. **1900 全年 / 2100-12-31 之后**：数据只为契约范围 1901-01-01..2100-12-31 负责；范围外的 `fromEpoch`/`nextSpringFestival` 为收敛或占位推定值（见 §5）。
3. **HKO 口径**：采用香港天文台公众年历（民用置闰）。若与其它万年历工具在个别年份/闰月口径上存在差异，以 HKO 为准（本项目数据契约如此规定）。
4. **`MONTH_NAMES` 用「冬月/腊月」**（契约 §8.2）：与 HKO 原始文本的「十一月/十二月」不同，但月号映射一致；UI 文案（如「农历腊月初八」）沿用契约。
5. `lastTermBefore` 在 1901-01-01..01-04 返回 `null`；`nextTermAfter` 在 2100 冬至之后返回 `null`。Store/UI 使用处应判空（当前 `30-store.js` 仅用 `lastTermBefore` 于今天，正常年份不受影响）。
